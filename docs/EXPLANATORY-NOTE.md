# Пояснительная записка

**Проект:** Диспетчер обращений по авариям и заявкам
**Трек:** «Умный город»
**Хакатон:** MAX, демо — 30.09.2026
**Статус на момент записки:** Д-10, MVP каркаса

## 1. Проблема

Житель, столкнувшись с аварией или неисправностью в доме (протечка, свет в
подъезде, лифт и т.п.), сегодня чаще всего либо не знает, куда обращаться,
либо вынужден звонить/писать в разные инстанции по разным каналам. Заявки
теряются на стыке «сообщил — зафиксировали — передали исполнителю»,
а обратной связи по статусу обычно нет.

## 2. Решение

Чат-бот в мессенджере MAX, который выступает диспетчером: житель описывает
проблему в свободном чате, бот доводит диалог до структурированной заявки
(что случилось, где, у кого) и передаёт её дальше по адресу — исполнителю
или в соответствующую службу. Канал выбран осознанно: MAX — сложившаяся
точка присутствия жителей, не нужно ставить отдельное приложение.

## 3. Архитектура

Монорепозиторий из трёх независимых сервисов и общих справочников:

```
bot/      диалог с жителем через MAX Bot API (long polling)
api/      бизнес-логика (Fastify)
db/       миграции PostgreSQL
config/   houses.json, rules.yaml, norms.yaml — справочники
docs/     max-notes.md — источник правды по MAX Bot API
```

Каждый сервис — самостоятельный npm-пакет со своим `Dockerfile`; общего
корневого `package.json` и workspaces нет намеренно — для MVP лишняя
связность не оправдана, сервисы собираются и деплоятся независимо.
Оркестрация — `docker-compose.yml`, три контейнера (`bot`, `api`, `db`)
поднимаются одной командой (см. [RUN.md](RUN.md)).

## 4. Технологический стек

| Компонент | Выбор | Обоснование |
|---|---|---|
| Язык | TypeScript / Node.js 22 | статическая типизация на скорость итераций хакатона, нативный `fetch` |
| Диалог с MAX | Свой клиент на `fetch`, без SDK | см. п. 6 — сторонние SDK на момент проверки ходили в устаревший API |
| Транспорт MAX | Long polling | не требует публичного HTTPS-домена и туннеля — критично для развёртывания на хакатоне; webhook — кандидат для продакшена позже |
| API | Fastify | лёгкий, минимальный оверхед для MVP-каркаса |
| БД | PostgreSQL 16 | реляционная модель подходит заявкам со статусами и связями «дом — заявка — исполнитель» |
| Инфраструктура | docker-compose | воспроизводимый запуск одной командой на любой машине |

## 5. Статус на Д-10

**Сделано и проверено вживую (на реальном трафике в MAX):**

- рабочий `/start` и эхо — бот отвечает реальным пользователям;
- docker-compose поднимает все три сервиса одной командой, `api` отдаёт
  `/health`, `db` — со health check;
- секреты только в `.env`, автоматическая проверка перед каждым коммитом
  (`.githooks/pre-commit` → `scripts/check-secrets.sh`).

**Сознательно не сделано сегодня** (см. правило согласования в
[`CONTRIBUTING.md`](../CONTRIBUTING.md)) — логика конечного автомата диалога с жителем
и схема БД не проектируются без явного решения команды: ошибка в этих двух
местах на раннем этапе стоит дороже всего остального. Также не начаты:
контракт API, миграции, маршрутизация заявок исполнителям, содержимое
`config/`-справочников.

## 6. Ключевые технические решения и трудности

Ниже — не рутинные шаги, а места, где готовые рецепты не сработали и
потребовалось разобраться заново. Подробности и способы диагностики
зафиксированы в [`docs/max-notes.md`](max-notes.md), здесь — только суть.

**MAX Bot API сменил контракт в июле 2026.** Базовый домен, способ передачи
токена (раньше — query-параметром, теперь — только заголовком
`Authorization`) — сторонние туториалы и как минимум один проверенный
npm-SDK на момент разработки всё ещё указывали на старый, недействующий
API. Решение — свериться с официальной документацией напрямую и написать
тонкий собственный клиент вместо стороннего SDK.

**`platform-api2.max.ru` не проходит проверку сертификата в Node.js «из
коробки».** Сервер подписан цепочкой Russian Trusted CA (Минцифры РФ) —
Windows и браузеры ей доверяют, встроенный список доверенных центров
сертификации у Node.js — нет. Ошибка проявляется как сетевой сбой, а не
как понятная ошибка авторизации, что осложняет диагностику. Решение —
сертификат снят с боевого сервера, проверен независимо от Node
(`openssl verify`) и передаётся через `NODE_EXTRA_CA_CERTS`, зашитую
в образ и в переменные окружения.

**Оба варианта запуска бота — `bot_started` (нажатие кнопки «Старт») и
`/start`, напечатанный вручную — обрабатываются отдельно.** Это два разных
события MAX Bot API; событие `message_created` при нажатии кнопки не
приходит вовсе. Без явной обработки `bot_started` бот молчал бы ровно на
первом экране, который видит любой новый пользователь.

## 7. Безопасность

- Токен бота — только в `.env` (вне git), в `.env.example` — плейсхолдеры.
- В коде нет ни одного захардкоженного секрета и ни одного фолбэка на него.
- Перед каждым коммитом автоматически проверяется, что в staged-файлах нет
  ключей, паролей и токеноподобных строк (`scripts/check-secrets.sh`).
- Полный аудит истории git на предмет секретов — отдельная задача,
  запланирована на Д-3.

## 8. Как запустить

Подробная инструкция — [`docs/RUN.md`](RUN.md). Коротко:

```bash
cp .env.example .env   # вписать MAX_BOT_TOKEN
docker compose up --build
```

## 9. Дальнейшие шаги

По порядку, ближе к демо:

1. Согласовать и реализовать конечный автомат диалога жителя (сбор адреса,
   категории проблемы, подтверждение) и схему БД.
2. Контракт `api` — приём заявок от `bot`, хранение, статусы.
3. Миграции `db`, наполнение `config/`-справочников.
4. Маршрутизация заявок исполнителям.
5. Аудит истории git на секреты (Д-3).

### Отложено сознательно — не входит в текущий сценарий

- **Передача показаний счётчиков с фотографией** — ещё один тип заявки ЖКХ.
  Предложено 24.09.2026, решено вернуться к нему **после КТ-2/КТ-3**, когда
  стабилизируется основной сценарий (авторизация → чат дома → заявка). В текущую
  реализацию не включается. Потребует загрузки файлов в мини-приложении и хранения
  фото — отдельное решение по схеме БД.
