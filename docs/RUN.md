# Запуск проекта

Одна команда после однократной подготовки:

```bash
docker compose up --build
```

Поднимает все три сервиса — `bot`, `api`, `db` — с логами в консоль.
Если возвращать терминал сразу, а логи смотреть отдельно: `docker compose up --build -d`,
дальше `docker compose logs -f bot`.

Порядок запуска гарантирован и выглядит так:

```
db (healthy) → migrate (применил миграции, вышел с кодом 0) → api (healthy) → bot
```

Миграции применяются **автоматически**, отдельной команды не нужно.

## Перед первым запуском (один раз)

1. **Docker Desktop.** Нужен запущенным (не только установленным) — движок
   стартует не сразу после установки/перезагрузки, ему требуется время на
   инициализацию WSL2-бэкенда. Готовность проверяется командой `docker info` —
   если она отвечает без ошибок, можно запускать `docker compose up`.

2. **`.env`.** Скопировать шаблон и вписать токен бота:

   ```bash
   cp .env.example .env
   ```

   В `.env` заполнить `MAX_BOT_TOKEN` (взять у @MasterBot в MAX). Остальные
   переменные уже имеют рабочие значения по умолчанию — трогать не обязательно.
   `.env` в `.gitignore`, коммитить его нельзя ни при каких условиях.

3. **pre-commit хук секретов** (не влияет на запуск, но нужен перед первым коммитом):

   ```bash
   git config core.hooksPath .githooks
   ```

## Проверка, что всё живо

```bash
curl http://localhost:3000/health
```

Ожидается `{"status":"ok","service":"api","db":"ok",...}`. Если `db` вернулся
`"down"`, а статус `degraded` (HTTP 503) — сервис жив, но не видит базу.

В MAX — написать боту `/start` (или нажать кнопку «Старт» в новом диалоге).
Вход — по номеру телефона, который УК заранее завела в базу (для проверки —
`SEED_TEST_PHONES` в `.env` и `docker compose run --rm migrate npm run seed`,
см. [`db/README.md`](../db/README.md)):

1. бот просит поделиться контактом и показывает кнопку «Поделиться контактом»;
2. после нажатия отвечает «Готово, вы вошли. **Номер жителя: N**».

Номер жителя означает, что цепочка MAX → бот → api → БД прошла целиком. Вместе
с ним приходит меню: «Чат дома» и «Отправить заявку ЖКХ». Дальше на `/start` —
«С возвращением! Номер жителя: N» и меню, на любой текст — меню.

«Чат дома» показывает адрес дома и кнопку-ссылку на чат (`houses.chat_link`,
у seed — `SEED_HOUSE_CHAT_LINK` для первого дома). Если дом жителя неизвестен,
бот просит адрес (из тестовых данных — «Полевая 7»). Вход по QR дома — ссылка
`https://max.ru/<username_бота>?start=<invite_code>`; коды домов:

```bash
docker compose exec db psql -U max -d max_dispatcher -c "SELECT id, address, invite_code FROM houses"
```

Кнопка «Отправить заявку ЖКХ» открывает мини-приложение внутри MAX, только если
его URL привязан к боту в `business.max.ru` (см. [`max-notes.md`](max-notes.md),
«Подключение мини-приложения к боту»).

Убедиться, что привязка действительно в базе:

```bash
docker compose exec db psql -U max -d max_dispatcher -c "SELECT id, max_chat_id, max_user_id FROM residents;"
```

Если бот отвечает «Сервис временно недоступен» — api не ответил. Бот в этом
случае намеренно не молчит; причина будет в `docker compose logs bot` строкой
«api недоступен при …».

## Работа с БД

Консоль psql:

```bash
docker compose exec db psql -U max -d max_dispatcher
```

Применить новые миграции вручную:

```bash
docker compose run --rm migrate
```

Откатить последнюю миграцию:

```bash
docker compose run --rm migrate npm run migrate:down
```

Загрузить **тестовые** организации и дома (не для продакшена):

```bash
docker compose run --rm migrate npm run seed
```

Подробности про миграции — [`db/README.md`](../db/README.md).

Если бот в MAX не отвечает, а `docker compose ps` показывает все три
контейнера `Up`/`healthy` — смотреть `docker compose logs bot`. Частая
причина ошибок — TLS/сертификат, см. «Проблемы» ниже.

## Правила маршрутизации

Кому уходит заявка и какой у неё срок, api решает по
[`config/rules.yaml`](../config/rules.yaml). Файл монтируется в контейнер api
только для чтения, поэтому после правки достаточно перезапуска, без пересборки:

```bash
docker compose restart api
docker compose logs api | grep "правила маршрутизации"
```

Вторая команда покажет, сколько правил загружено.

С ошибкой в файле api не стартует и называет правило и поле, например:
`config/rules.yaml, правило heating_outage: responsible «rso_teplo» не из
responsible_categories`.

Проверить правила на тестах Павла (`docs/routing-test-cases.json`) — без Docker:

```bash
cd api && npm install && npm test
```

## Дома и жители: команда УК

**Следующий шаг после `docker compose up`.** Бот пускает только тех жителей,
которых заранее завела управляющая компания: житель делится в боте номером
телефона, и бот ищет этот номер в списке УК. Пока список пуст, войти не сможет
никто. Ниже — как его заполнить.

Инструкция для сотрудника УК или его подрядчика. Нужен доступ к серверу, где
запущен проект, — командная строка в папке проекта (там, где лежит
`docker-compose.yml`). Всё делается одной командой с разными словами после неё;
SQL и доступ к базе не нужны.

Как устроено хранение и почему так — [`db-overview.md`](db-overview.md).

### Шаг 0. Короткое имя для команды

Полная команда длинная: `docker compose exec api node dist/cli.js …`. Чтобы не
набирать её каждый раз, один раз за сеанс выполните:

```bash
alias uk='docker compose exec api node dist/cli.js'
```

Дальше во всех примерах — `uk`. Проверьте, что работает: `uk` без слов
печатает справку со всеми командами.

Если в ответ `service "api" is not running` — проект не запущен:
`docker compose up -d` и повторить.

### Шаг 1. Завести дома

Сначала дома — жителей заводят уже в конкретный дом.

```bash
uk houses add --address "г. Тестоград, ул. Новая, д. 7 к 2" --chat https://max.ru/join/…
```

```
#4  г. Тестоград, ул. Новая, д. 7 к 2
     жителей: 0   чат: https://max.ru/join/…   код QR: 01a4bb1e582a
```

- `#4` — номер дома в системе, пригодится дальше.
- **Адрес** пишите как в документах УК. Система сама выделит улицу и номер дома
  («ул.», «д.», город и регистр букв не важны) — по ним житель потом найдёт
  дом, введя адрес в боте в любом виде.
- **`--chat`** — ссылка-приглашение в чат дома в MAX, необязательно. Можно
  добавить позже.
- **Код QR** — для QR-кода в подъезде. Ссылка в QR:
  `https://max.ru/<имя_бота>?start=<код>`. Житель, отсканировав его, входит в бота, и
  бот сразу знает его дом и чат — даже если УК не указала ему дом.

Список всех домов — `uk houses list`. Изменить адрес или ссылку на чат:

```bash
uk houses edit 4 --chat https://max.ru/join/новая-ссылка
uk houses edit 4 --chat -
```

`--chat -` убирает ссылку.

Возможные ошибки:

| Сообщение | Что значит |
|---|---|
| `Не удалось выделить улицу и номер дома` | в адресе нет номера дома или названия улицы — допишите |
| `Запись с такими данными уже существует` | такой дом уже заведён — посмотрите `uk houses list` |

### Шаг 2а. Завести жителя вручную

Подходит, когда жителей немного или нужно добавить одного.

```bash
uk residents add --phone "8 999 000-00-02" --address "Новая 7к2" \
                 --entrance 2 --floor 5 --apartment 45А --contract Д-123
```

```
#2  +79990000002  г. Тестоград, ул. Новая, д. 7 к 2, под. 2, эт. 5, кв. 45А
     договор: Д-123   вошёл в бота: нет
```

- **`--phone`** — обязательно. В любом виде: `+7…`, `8…`, с пробелами и
  скобками. Номер должен быть тот, что привязан к MAX у жителя.
- **Дом** — `--address` (как в шаге 1, в любом виде) или `--house 4` (номер
  дома из `uk houses list`).
- **`--name`** — ФИО жителя, по желанию: `--name "Иванов Иван Иванович"` (кириллица
  или латиница). `--name -` — стереть. Жителю нигде не показывается — справка для УК.
- **`--entrance`, `--floor`, `--apartment`, `--contract`** — подъезд, этаж,
  квартира, номер договора. Все необязательные. Номер договора житель нигде не
  вводит — это справка для УК.
- Несколько жильцов одной квартиры — это несколько записей с разными телефонами
  и одинаковой квартирой.
- Дом, подъезд, этаж, квартира и договор здесь — **основная** квартира жителя.
  Вторая и следующие (в том числе в других домах) заводятся в pgAdmin, таблица
  `resident_premises` — см. «Работа УК в pgAdmin».
- `вошёл в бота: нет` — житель ещё не входил. После входа станет `да`.

Проверить, кто заведён в дом: `uk residents list --house 4`, найти по телефону:
`uk residents list --phone 89990000002`.

### Шаг 2б. Загрузить жителей из Excel

Подходит для первоначальной загрузки всего списка. **Подробная инструкция —
как оформить таблицу, подводные камни Excel, разбор ошибок, готовый шаблон —
[`excel-import.md`](excel-import.md).** Ниже — кратко.

**1. Подготовить таблицу.** Первая строка — заголовки, дальше по жителю в
строке. Порядок столбцов любой, лишние столбцы игнорируются.

| телефон | адрес | ФИО | подъезд | этаж | квартира | договор |
|---|---|---|---|---|---|---|
| +7 999 000-00-21 | г. Тестоград, ул. Примерная, д. 1 | Иванов Иван Иванович | 1 | 3 | 12 | Д-21 |
| 89990000022 | Примерная 3 | | 2 | | 15А | |

Обязательны «телефон» и «адрес», остальное можно оставить пустым. Дома из
столбца «адрес» должны быть заведены заранее (шаг 1).

**2. Сохранить как CSV.** В Excel: «Файл → Сохранить как → CSV (разделители —
запятые)» или «CSV UTF-8». Подходят оба.

**3. Положить файл на сервер** в папку проекта (например, через WinSCP или
`scp жители.csv сервер:~/max-dispatcher/`).

**4. Проверить без записи** — `--dry-run`:

```bash
docker compose exec -T api node dist/cli.js residents import - --dry-run < жители.csv
```

```
Будет: новых жителей 2, обновлённых 1, строк с ошибками 2.
  строка 5: телефон не похож на номер из 10 цифр после +7
  строка 6: Дом с таким адресом не заведён — сначала houses add
Проверка (--dry-run): ничего не записано.
```

Здесь `-T` и `< жители.csv` — не опечатка: так файл передаётся команде. Алиас
`uk` для импорта не подходит, пишите команду целиком.

Номер строки — как в Excel (заголовки — строка 1), если в таблице нет пустых
строк: пустые пропускаются и в счёт не идут. Телефоны в отчёт не
выводятся намеренно. Исправьте строки с ошибками и повторите проверку, пока
ошибок не останется.

**5. Загрузить** — та же команда без `--dry-run`:

```bash
docker compose exec -T api node dist/cli.js residents import - < жители.csv
```

```
Готово: новых жителей 2, обновлённых 1, строк с ошибками 0.
```

Как импорт обращается с данными:

- Житель с таким телефоном уже есть — его данные **обновляются**, новой записи
  не будет. Поэтому файл можно загружать повторно, например после правок.
- Пустая ячейка — значение **не меняется**. `-` в ячейке — значение
  **стирается**.
- Кого нет в файле — **не трогаются**. Убрать жителя — только командой из шага 3.
- Строки с ошибками пропускаются, остальные загружаются. Повторная загрузка
  исправленного файла ничего не задвоит.

### Шаг 3. Изменить или убрать жителя

Номер жителя (`#12`) — из `uk residents list`.

Поменять квартиру:

```bash
uk residents edit 12 --apartment 46
```

Стереть этаж:

```bash
uk residents edit 12 --floor -
```

Переезд:

```bash
uk residents edit 12 --address "Примерная 1" --entrance 1 --apartment 7
```

Новый номер телефона:

```bash
uk residents edit 12 --phone +79990000001
```

- **Переезд.** Старые заявки жителя остаются на прежнем адресе.
- **Новый телефон.** Жителю придётся войти в бота заново с новым номером:
  подтверждён был старый. Команда предупредит об этом.

Житель съехал:

```bash
uk residents archive 12
```

```
#12  +79990000012  г. Тестоград, ул. Новая, д. 7 к 2, под. 2
     договор: Д-123   вошёл в бота: нет   В АРХИВЕ с 2026-09-24
```

Жителя нельзя удалить совсем — только перевести в архив. В бота он больше не
войдёт, но его заявки и история по адресу сохранятся. Если человек вернётся или
его номер получит новый жилец — заведите заново (шаг 2а). Архивных видно с
флагом `--archived`: `uk residents list --archived`. Изменить архивного нельзя —
команда ответит `Житель в архиве — изменения запрещены`.

### Шаг 4. Заявки: посмотреть и сменить статус

```bash
uk tickets list --active
uk tickets list --house 4
uk tickets status 12 в_работе
```

- `--active` — только незакрытые, новые сверху;
- `--house 4` — заявки одного дома;
- статус — `принята`, `в_работе`, `решена` или `отменена`.

```
#12  [в работе]  heating · whole_house  2026-09-26
     г. Заречный, ул. Полевая, д. 5   ответственный: АО «Теплосеть»   правило: heating_outage
Статус изменён — житель получит уведомление.
```

Через несколько секунд бот сам пишет жителю: «Заявка №12 взята в работу» /
«решена ✅». Повторно тот же статус — ничего не меняется и не отправляется.

### Для разработчиков

Команда — [`api/src/cli.ts`](../api/src/cli.ts); она ходит в маршруты
`/admin/*` того же api, контракт — [`api.md`](api.md), «Дома и жители — для
УК». Снаружи эти маршруты закрыты: nginx их не публикует, а api отвечает 404 на
любые запросы через прокси. Входа для сотрудников УК нет, поэтому управление —
только с сервера.

## Работа УК в pgAdmin (демо)

То же, что команда УК, но мышкой в таблицах — без консоли сервера и без SQL.
Для демо: работает сам разработчик. Настоящим сотрудникам доступ к базе не
выдаётся — для них будет экран диспетчера в мини-приложении (решение 26.09.2026).

Правка в таблицах даёт тот же результат, что и команда УК: база сама приводит
телефон к виду `+7…`, пишет событие при смене статуса (житель получает
уведомление), снимает привязку к MAX при архиве и смене номера; api раз в минуту
разбирает адрес нового дома на улицу и номер (миграция `0007`).

### Подключение

База слушает только сам сервер, поэтому pgAdmin подключается через SSH-туннель.
Свойства сервера в pgAdmin:

| Вкладка | Поле | Значение |
|---|---|---|
| Connection | Host | `127.0.0.1` |
| Connection | Port | `5433` (`DB_PORT` из `.env` на сервере) |
| Connection | Maintenance database / Username | `max_dispatcher` / `max` |
| SSH Tunnel | Tunnel host / Username | адрес сервера / пользователь SSH |

### По-русски: представления

Рядом с английскими таблицами — русские представления (миграции `0010`, `0011`):
**Schemas → public → Views**: `жители`, `квартиры`, `дома`, `организации`,
`организации_дома`, `заявки`, `история_заявок`. Каждое — зеркало своей
таблицы один в один: те же столбцы в том же порядке, строки по возрастанию
номера. Только в конце добавлены `статус_словами`, `тип_словами`,
`событие_словами`, `роль_словами`. Подсказки к английским столбцам — в их
свойствах (Properties → Comment).

**Сверять правку:** откройте таблицу (например, `residents`) и её
представление (`жители`) через View/Edit Data и перетащите одну вкладку к
правому краю окна pgAdmin — они встанут рядом. Правите в английской, после
сохранения (F6) обновите русскую (F5) — столбец N там тот же, что в таблице.

- **Смотреть** — правой кнопкой по представлению → View/Edit Data → All Rows.
  Мышкой в представлении pgAdmin **не правит** (у представления нет первичного
  ключа) — правка мышкой по-прежнему в таблицах, как ниже.
- **Править по-русски** — SQL в **Tools → Query Tool** (▶ или F5). Имена с
  заглавными буквами — в кавычках:

  ```sql
  SELECT номер, статус_словами, тип_словами, подана FROM заявки ORDER BY номер DESC;
  UPDATE заявки SET статус = 'in_progress' WHERE номер = 5;   -- житель получит уведомление
  UPDATE жители SET "ФИО" = 'Иванов Иван Иванович' WHERE номер = 3;
  SELECT * FROM история_заявок WHERE номер_заявки = 5 ORDER BY номер;
  ```

  Статус пишется кодом: `new`, `in_progress`, `resolved`, `cancelled`.
  Столбцы `…_словами` и `вошёл_в_бота` только для чтения.

### Как править таблицу

Таблицы: **Servers → сервер → Databases → max_dispatcher → Schemas → public → Tables**.

1. Правой кнопкой по таблице → **View/Edit Data → All Rows**.
2. Изменить значение — двойной щелчок по ячейке. Новая строка — пустая строка
   внизу таблицы.
3. **Сохранить — кнопка «Save Data Changes» (F6).** Без неё ничего не запишется.

Поля, которые **не заполнять** (заполнятся сами): `id`, `created_at`,
`updated_at`, у домов — `street`, `number`, `invite_code`, у жителей —
`max_user_id`, `max_chat_id`. Строки **не удалять**: у жителей и домов есть
заявки, удаление либо не пройдёт, либо сотрёт историю.

### Новый дом — таблица `houses`

| Поле | Что вписать |
|---|---|
| `address` | полный адрес: `г. Заречный, ул. Садовая, д. 10` |
| `organization_id` | номер УК из таблицы `organizations` (например, УК Маяк) |
| `emergency_phone` | телефон аварийной службы дома; пусто — бот скажет «звоните 112» |
| `has_gas` | `true` — в доме газ; `false` — электроплиты, бот не покажет «Запах газа» |
| `timezone` | часовой пояс дома, по умолчанию `Europe/Moscow`; например `Asia/Yekaterinburg` — по нему бот пишет время подачи заявки |
| `chat_link` | ссылка-приглашение в чат дома (см. ниже), можно позже |

Через минуту у дома появятся `street`, `number` и `invite_code` — дом готов.
QR-код в подъезд: `https://max.ru/<имя_бота>?start=<invite_code>`.

**Ресурсоснабжающие организации дома** — таблица `house_organizations`, по строке
на каждую: `house_id` — номер дома, `role` — `water`, `heat`, `electricity` или
`gas`, `organization_id` — номер организации из `organizations`. Без них у заявок
на отопление, воду и свет не будет ответственного.

### Чат дома в MAX

Создать чат бот не может — в приложении MAX создайте групповой чат, в его
настройках скопируйте ссылку-приглашение и вставьте в `houses.chat_link`. Житель
увидит кнопку «Перейти в чат дома».

### Новый житель — таблицы `residents` и `resident_premises`

Житель — это человек (`residents`), его квартиры — отдельными строками
(`resident_premises`, миграция `0009`). Сначала житель:

| Поле | Что вписать |
|---|---|
| `phone` | телефон в любом виде: `8 900 123-45-67`, `+79001234567` |
| `full_name` | ФИО, по желанию |

Потом его квартира — строка в `resident_premises`:

| Поле | Что вписать |
|---|---|
| `resident_id` | номер жителя (`id` из `residents`) |
| `house_id` | номер дома из `houses` |
| `entrance`, `floor`, `apartment`, `contract_number` | по желанию |

**Квартиры в нескольких домах** — ещё строки в `resident_premises` с тем же
`resident_id` и другим `house_id`. Бот и мини-апп тогда спрашивают «В каком доме
проблема?», а «Чат дома» предлагает выбрать дом. Основная квартира — строка,
заведённая первой. Та же квартира дважды не заводится (защита от двойного ввода).

Житель пишет боту `/start` → «Поделиться контактом» — готово. Номер должен быть
тем, что привязан к MAX у жителя.

**Изменить** — поправить ячейку. Новый телефон — житель войдёт в бота заново.
**Убрать** — не удалять строку, а вписать в `archived_at` слово `now` (сейчас):
войти он больше не сможет, заявки останутся.

### Заявки — таблица `tickets`

Сменить статус: колонка `status` → `in_progress` (в работе), `resolved`
(решена) или `cancelled` (отменена) → **F6**. Через несколько секунд бот сам напишет жителю. Другие колонки
заявки не трогать.

Посмотреть заявки понятно — **Tools → Query Tool**, вставить и нажать ▶ (F5):

```sql
SELECT t.id AS "№", t.status AS "статус", t.problem_type AS "что", t.place AS "где",
       h.address AS "адрес", o.name AS "исполнитель", t.description AS "описание",
       t.created_at AS "подана"
FROM tickets t
LEFT JOIN houses h ON h.id = t.house_id
LEFT JOIN organizations o ON o.id = t.assigned_organization_id
ORDER BY t.id DESC;
```

### Доступ с сервера к приватному репозиторию

Репозиторий приватный — серверу нужна авторизация. Стандартный способ для
такого сценария (неинтерактивный скрипт, доступ только на чтение) —
**deploy-key**, а не личный SSH-ключ и не голый PAT:

- **Личный SSH-ключ**, скопированный на VPS, — при компрометации сервера
  под угрозой весь аккаунт GitHub, а не только этот репозиторий.
- **PAT** через HTTPS работает, но токен легко случайно засветить
  (история шелла, вывод `ps`), и по умолчанию он не привязан к одному репо.
- **Deploy-key** — ключ для конкретного репозитория, можно ограничить
  только чтением (клонировать/`pull` можно, пушить нельзя). Утечёт — под
  угрозой ровно один репозиторий.

```bash
ssh-keygen -t ed25519 -f ~/.ssh/max_deploy_key -N "" -C "vps-deploy"
cat ~/.ssh/max_deploy_key.pub
```

Публичный ключ → GitHub → репозиторий → **Settings → Deploy keys →
Add deploy key**, галочку «Allow write access» **не ставить**.

Затем указать git, каким ключом пользоваться для github.com, и заранее
принять ключ хоста (иначе первый `git clone` в неинтерактивном скрипте
упадёт на вопросе `Are you sure you want to continue connecting?`):

```bash
cat >> ~/.ssh/config <<'EOF'
Host github.com
  HostName github.com
  User git
  IdentityFile ~/.ssh/max_deploy_key
  IdentitiesOnly yes
EOF
chmod 600 ~/.ssh/config
ssh-keyscan -t ed25519 github.com >> ~/.ssh/known_hosts
```

После этого `git clone git@github.com:EEGRINO/magistral-dispatcher-max.git`
с сервера работает.

развёрнутый `.env` сама не попадёт — это осознанно (`.env` никогда не
затирается автоматически), добавлять руками.

### Домен и TLS: nginx + certbot

> 💡 Всё это — сборку мини-аппа, оба конфига nginx, certbot и ufw — делает
> [`scripts/deploy-vps.sh`](../scripts/deploy-vps.sh), если ответить «да» на
> «Настроить nginx?». Его конфиги — `/etc/nginx/sites-available/max-dispatcher-*`;
> домен, уже описанный в другом конфиге, скрипт не трогает. Ниже — то же руками.

Два поддомена — один на `api`, второй на статику мини-аппа. Контейнеры
80/443 не публикуют вообще: `db` и `api` в `docker-compose.yml` привязаны
к `127.0.0.1`, наружу отдаёт только системный nginx.

> Было решение поднимать Caddy отдельным сервисом в compose — **отменено**.
> На сервере уже стоял системный nginx, и Caddy с ним боролся за 80/443:
> кто стартовал раньше после перезагрузки, тот и держал порт, второй падал
> с `Address already in use`. Решение задним числом не масштабировалось —
> проще держать один TLS-терминатор, чем гонять входной трафик через два.

**1. Собрать статику мини-аппа на хост** (Node на хосте не нужен — сборка
идёт в одноразовом контейнере):

```bash
sudo mkdir -p /var/www/magistralbot
docker compose --profile deploy run --rm miniapp-build
```

Повторять при каждом обновлении `miniapp/` — сервис не запускается сам по
себе с обычным `docker compose up` (см. комментарий `profiles` в
`docker-compose.yml`).

**2. Конфиги nginx.** Порт api берётся из `.env`, не хардкодится:

```bash
API_PORT="$(sed -n 's|^API_PORT=||p' ~/путь_до_папки_проекта/.env | tail -n1)"
API_PORT="${API_PORT:-3000}"
```

> ⚠️ **Наружу — только явно перечисленные пути, всё остальное — `404`.**
> Не `location / { proxy_pass … }` на весь api: 24.09.2026 именно так наружу
> оказался открыт внутренний `POST /residents/link-by-phone`, через который можно
> было привязать к себе чужую квартиру. Эндпоинты для бота живут только в сети
> compose; api дополнительно сам отвечает 404 на `/residents/*` через прокси
> (`docs/api.md`), но это вторая линия, а не повод открывать всё.

`/etc/nginx/sites-available/api.ВАШ-ДОМЕН` — наружу только `/health`:

```nginx
server {
    listen 80;
    server_name api.ВАШ-ДОМЕН;

    location = /health {
        proxy_pass http://127.0.0.1:PORT;   # подставить $API_PORT
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location / {
        return 404;
    }
}
```

`/etc/nginx/sites-available/miniapp.ВАШ-ДОМЕН` — статика плюс те маршруты api,
которые нужны мини-аппу, под тем же origin (мини-апп ходит на `/api/...`
same-origin, поэтому CORS в `api` не заведён). Каждый маршрут — отдельным
`location`; сейчас это только `/api/health`:

```nginx
server {
    listen 80;
    server_name miniapp.ВАШ-ДОМЕН;
    root /var/www/magistralbot;

    location /assets/ {
        add_header Cache-Control "public, max-age=31536000, immutable";
    }
    location / {
        try_files $uri $uri/ /index.html;
        add_header Cache-Control "no-cache";
    }
    # proxy_pass с путём заменяет совпавшую часть: /api/health → /health
    location = /api/health {
        proxy_pass http://127.0.0.1:PORT/health;   # подставить $API_PORT
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
    # Мини-приложение → api /app/*. Единственный путь api наружу, кроме health:
    # жителя api узнаёт по подписи initData MAX (api/src/routes/app.ts).
    location /api/app/ {
        proxy_pass http://127.0.0.1:PORT/app/;     # подставить $API_PORT
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        client_max_body_size 16k;                  # заявка — текст до 4000 символов
    }
    # Отдельный блок: иначе try_files отдал бы на неизвестный /api/... index.html с 200
    location /api/ {
        return 404;
    }
}
```

```bash
sudo ln -s /etc/nginx/sites-available/api.ВАШ-ДОМЕН /etc/nginx/sites-enabled/
sudo ln -s /etc/nginx/sites-available/miniapp.ВАШ-ДОМЕН /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
```

**3. Сертификаты** (certbot сам допишет SSL-директивы и редирект с 80 на 443
в уже существующие server block — конфиги из шага 2 должны быть на месте
до этой команды):

```bash
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d api.ВАШ-ДОМЕН -d miniapp.ВАШ-ДОМЕН
sudo certbot renew --dry-run
systemctl status certbot.timer
```

`renew --dry-run` проверяет автопродление, у `certbot.timer` статус должен быть `active`.

**4. Файрвол** — скрипты его не трогают:

```bash
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
```

**5. Проверка:**

```bash
curl -I https://api.ВАШ-ДОМЕН/health
curl -I https://miniapp.ВАШ-ДОМЕН
curl -I https://miniapp.ВАШ-ДОМЕН/api/health
```

Все три должны ответить `HTTP/2 200`: api, статика мини-аппа (`index.html`) и
прокси с домена мини-аппа на api.

`/health` через `/api/` отвечающий 503 — не проблема сертификата, это
`api` не видит БД (`docs/api.md`, раздел `GET /health`).

### Имя репозитория менялось — ловушка с именем каталога

Репозиторий переименовывали (`-MAX-` → `magistral-dispatcher-max`).
GitHub держит редирект со старого адреса какое-то время, но полагаться
на него не стоит — если `git remote -v` на сервере показывает старый
адрес, поправить: `git remote set-url origin git@github.com:EEGRINO/magistral-dispatcher-max.git`.

Отдельно: если репозиторий когда-то склонировали без явного каталога (в том
числе вручную, не через `deploy-vps.sh`), каталог получит имя со старого
клонирования — в частности, `-MAX-` начинается с дефиса, и относительные
команды вида `cd -MAX-` или `mv -MAX- куда-то` разбираются шеллом как
флаги, а не как имя каталога. Лечится либо полным путём (`cd /root/-MAX-`
работает нормально — дефис опасен только в начале relative-аргумента),
либо явным `--` (`mv -- -MAX- новое-имя`). `deploy-vps.sh` поэтому всегда
спрашивает каталог установки явно (по умолчанию `/opt/max-dispatcher`), а не
полагается на то, как git назовёт каталог сам.

## Проблемы, с которыми реально столкнулись при первом запуске

Ничего из этого не баг в коде проекта — пункты воспроизводимы на любой
свежей машине и стоят внимания при подготовке следующего компьютера к демо.

### Сервер: зарубежный VPS не видит MAX, российский — не видит Docker (27.09.2026)

- **Сервер должен быть в России:** с VPS в Финляндии `platform-api2.max.ru`
  не принимает соединения — бот не работает (`docs/max-notes.md`).
- **Из России закрыт Docker:** `download.docker.com` (установка Docker) и
  `registry-1.docker.io` (образы `postgres`, `node`) — тайм-аут TLS. Установщик
  обходит оба: ставит Docker из репозитория Ubuntu (`docker.io`,
  `docker-compose-v2`, `docker-buildx`) и прописывает зеркало реестра в
  `/etc/docker/daemon.json` (`mirror.gcr.io`, `dockerhub.timeweb.cloud` —
  проверены 27.09.2026, отдают наши образы). Руками то же самое:

  ```bash
  apt-get install -y docker.io docker-compose-v2 docker-buildx
  printf '{\n  "registry-mirrors": ["https://mirror.gcr.io", "https://dockerhub.timeweb.cloud"]\n}\n' > /etc/docker/daemon.json
  systemctl restart docker
  ```

### `docker` / `node` не найдены сразу после установки

Установщики Node.js и Docker Desktop прописывают PATH в реестре Windows,
но уже открытый терминал его не подхватывает. **Открыть новый терминал**
(перезапуск текущего окна недостаточно, если это не полноценный новый
процесс) — после этого `node -v` и `docker --version` должны отвечать.

### `docker info` отвечает ошибкой про pipe / engine недоступен

Docker Desktop установлен, но само приложение не запущено — установка не
запускает его автоматически. Запустить Docker Desktop из меню Пуск (или
с рабочего стола) и подождать: значок в трее должен перестать «крутиться».
Если после запуска `docker info` минуту-другую отвечает `500 Internal
Server Error` — двигатель ещё поднимает WSL2-бэкенд, это нормально при
первом старте, достаточно подождать.

### Docker Desktop зависает на инициализации бэкенда надолго (не 1-2 минуты, а постоянно)

Значит на машине не установлен WSL2 — Docker Desktop на Windows требует
его по умолчанию. Проверяется командой `wsl --status`. Если WSL не
установлен — `wsl --install` **от администратора**, затем обязательная
**перезагрузка**. После перезагрузки заново запустить Docker Desktop
(автостарт после установки WSL не гарантирован).

### Бот падает с `fetch failed` / `unable to get local issuer certificate`

Это не сеть и не токен. `platform-api2.max.ru` подписан сертификатом
Russian Trusted CA (Минцифры РФ), которого нет во встроенном списке
доверенных CA у Node.js. Решение уже реализовано в проекте
(`NODE_EXTRA_CA_CERTS` → `bot/certs/`) и работает «из коробки» и в Docker,
и локально — если ошибка всё же появилась, разбор в
[`docs/max-notes.md`](max-notes.md#️-tls-nodejs-не-доверяет-сертификату-platform-api2maxru-из-коробки).

### `migrate` падает с `getaddrinfo ENOTFOUND db`, хотя `db` «healthy»

Проверено 24.09.2026 на сервере, где уже стоял системный PostgreSQL.

Симптом сбивает с толку: `db` в статусе `healthy`, в его логах
`ready to accept connections`, а `migrate` не находит имя `db`; `api` и
`bot` висят в `Created`. Настоящая причина — **порт 5432 на хосте занят**
(обычно системным Postgres, `systemctl is-active postgresql`). Docker не
может пробросить порт и оставляет контейнер `db` **без сети**. Healthcheck
при этом зелёный — `pg_isready` ходит через unix-сокет внутри контейнера,
сеть ему не нужна. Встроенный DNS сети compose про `db` не знает и пересылает
запрос во внешний DNS, отсюда именно `ENOTFOUND`, а не отказ соединения.

Диагностика:

```bash
docker inspect max-dispatcher-db-1 --format '{{json .NetworkSettings.Networks}}'
sudo ss -ltnp 'sport = :5432'
```

`{}` в первой команде — у контейнера нет сети; вторая показывает, кто держит порт.

Явная ошибка `failed to bind host port 127.0.0.1:5432/tcp: address already in use`
видна не всегда — при перезапуске контейнера демоном она уходит в журнал
Docker, а не в вывод `compose`.

Лечение — перенести наружный порт `db`, чужой Postgres не трогать:

```bash
sed -i 's/^DB_PORT=.*/DB_PORT=5433/' .env
docker compose down --remove-orphans && docker compose up -d
```

`DATABASE_URL` при этом **не менять**: в нём внутренний адрес `db:5432`.
