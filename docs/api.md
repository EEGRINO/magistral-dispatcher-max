эндпоинты, а не план: всё перечисленное ниже проверено запросами.

## Базовый адрес

| Окружение | Адрес |
|---|---|
| Локально (docker compose) | `http://localhost:3000` |
| Внутри сети compose | `http://api:3000` |

Порт задаётся переменной `API_PORT` (по умолчанию 3000).

## Общие правила

- Формат — JSON. Для запросов с телом обязателен заголовок
  `Content-Type: application/json`.
- Кодировка — UTF-8. Кириллица в полях поддерживается.
- **Идентификаторы — целые числа** (`number`), не строки. В БД это `BIGSERIAL`,
  драйвер приводит их к `number` (безопасно до 2^53).
- **Даты — строки ISO 8601 в UTC**, например `"2026-09-20T15:22:53.965Z"`.
- Поля в JSON — `snake_case`, как в БД.
- Лишние поля в теле запроса → ошибка `validation_error`, а не молчаливое
  игнорирование. Опечатка в имени поля обнаружится сразу.

### Формат ошибок

Любая ошибка возвращается в одинаковом виде:

```json
{
  "error": {
    "code": "not_found",
    "message": "Заявка 999 не найдена",
    "details": ["/problem_type must NOT have fewer than 1 characters"]
  }
}
```

- `code` — **часть контракта**, ветвиться в клиенте нужно по нему.
- `message` — текст для человека, формулировка может меняться.
- `details` — необязательное поле, присутствует только у `validation_error`.

### Коды ошибок

| HTTP | `code` | Когда |
|---|---|---|
| 400 | `validation_error` | тело не прошло проверку по схеме (тип, длина, лишнее поле) |
| 400 | `bad_request` | битый JSON, неверный `Content-Type`, несовпадение `Content-Length` |
| 400 | `invalid_reference` | ссылка на несуществующую запись (нарушение внешнего ключа) |
| 400 | `constraint_violation` | значение не прошло проверку на уровне БД |
| 404 | `not_found` | запрошенная сущность не найдена |
| 404 | `phone_not_registered` | номера нет среди жителей, заведённых УК |
| 404 | `house_not_found` | ни код из QR, ни введённый адрес не совпали ни с одним домом |
| 400 | `address_unrecognized` | во введённом адресе не нашлось пары «улица + номер дома» |
| 404 | `route_not_found` | такого маршрута не существует |
| 409 | `conflict` | запись с такими данными уже есть |
| 409 | `resident_archived` | житель в архиве — изменять его нельзя |
| 500 | `internal_error` | ошибка на стороне сервиса; подробности только в логах |
| 503 | — | только у `/health`, см. ниже |

## `GET /health`

Живость сервиса и соединения с БД. Используется healthcheck'ом docker-compose.

**Запрос:** без тела и параметров.

**Ответ 200** — всё работает:

```json
{
  "status": "ok",
  "service": "api",
  "db": "ok",
  "ts": "2026-09-20T15:22:40.692Z"
}
```

**Ответ 503** — сервис жив, но БД недоступна:

```json
{
  "status": "degraded",
  "service": "api",
  "db": "down",
  "ts": "2026-09-20T15:22:40.692Z"
}
```

Формат ответа одинаковый у 200 и 503 — ошибочного конверта здесь нет.

| Поле | Тип | Значения |
|---|---|---|
| `status` | string | `"ok"` \| `"degraded"` |
| `service` | string | всегда `"api"` |
| `db` | string | `"ok"` \| `"down"` |
| `ts` | string | ISO 8601 |

## Жители — только для бота

> ⚠️ **Все эндпоинты внутренние.** Их вызывает бот по сети compose
> (`http://api:3000`); через nginx наружу их публиковать **нельзя**. Подлинность
> номера проверяет бот — по подписи контакта MAX, которую можно посчитать только
> токеном бота (см. [`max-notes.md`](max-notes.md), «Контакт жителя»). api верит
> боту на слово: открытый наружу `link-by-phone` позволил бы привязать к себе
> чужую квартиру, просто назвав её номер.
>
> **`/residents/*` доступен только из внутренней сети compose; снаружи всегда 404,
> независимо от конфигурации nginx:** api сам отклоняет запросы с заголовками
> прокси `X-Real-IP` / `X-Forwarded-For` ответом `route_not_found`.

### `POST /residents/link-by-phone`

Привязывает диалог и пользователя MAX к жителю с этим номером. Житель должен
быть заранее заведён УК; сам эндпоинт жителей **не создаёт**. Жители в архиве
не находятся — для них ответ `phone_not_registered`. Идемпотентен:
повторный вход тем же аккаунтом ничего не меняет.

**Тело запроса:**

```json
{ "phone": "+79990000000", "max_chat_id": 516093921, "max_user_id": 163719150 }
```

| Поле | Тип | Обязательное | Ограничения |
|---|---|---|---|
| `phone` | string | да | ровно `+7` и 10 цифр — нормализует вызывающая сторона |
| `max_chat_id` | number | да | целое ≥ 1, `chat_id` диалога с ботом |
| `max_user_id` | number | да | целое ≥ 1, id пользователя MAX (`sender.user_id`) |

**Ответ 200:** `{ "resident": Resident }` — см. «Объект `Resident`» ниже.

**Ошибки:**

| HTTP | `code` | Когда |
|---|---|---|
| 404 | `phone_not_registered` | номера нет среди жителей УК — бот предлагает обратиться в УК |
| 409 | `conflict` | этот аккаунт/диалог MAX уже привязан к **другой** квартире (одна квартира на аккаунт) |
| 400 | `validation_error` | номер не в формате `+7XXXXXXXXXX` и т.п. |

Если квартира уже была привязана к **другому** аккаунту MAX, привязка
перезаписывается: номер подтверждён подписью MAX, значит сейчас он принадлежит
этому аккаунту. В лог api пишется предупреждение с id жителя (без номера).

### `GET /residents/by-max-user/:max_user_id`

Житель, к которому привязан пользователь MAX. По нему бот понимает, вошёл ли
человек, — отдельного хранилища состояния у бота нет.

**Ответ 200:** `{ "resident": Resident }`.
**Ошибки:** `not_found` (404) — этот пользователь ещё не входил; `validation_error` (400).

### Объект `Resident`

```json
{
  "id": 1,
  "house_id": 1,
  "max_chat_id": 516093921,
  "max_user_id": 163719150,
  "created_at": "2026-09-24T07:35:07.814Z"
}
```

| Поле | Тип | Может быть null | Смысл |
|---|---|---|---|
| `id` | number | нет | идентификатор жителя |
| `house_id` | number | да | дом, если известен |
| `max_chat_id` | number | да | `chat_id` диалога с ботом; `null` — ещё не входил |
| `max_user_id` | number | да | id пользователя MAX; `null` — ещё не входил |
| `created_at` | string | нет | ISO 8601 |

Телефона в объекте нет намеренно: это персональные данные, а клиентам он не нужен.

### Дом жителя — тоже только для бота

Все три маршрута под `/residents/…` и закрыты так же: снаружи — `404`.

**Правило для всех трёх:** дом жителя **заполняется, только если он ещё
неизвестен**. Данные УК главнее QR-кода и ручного ввода — уже указанный дом не
перезаписывается (решение 24.09.2026, [`Решения_проекта.md`](Решения_проекта.md)).

#### `GET /residents/:id/house`

**Ответ 200:** `{ "house": House }` или `{ "house": null }` — дом ещё неизвестен.
**Ошибки:** `not_found` (404) — нет такого жителя.

#### `POST /residents/:id/house-by-invite`

Дом по коду из QR / диплинка `https://max.ru/<бот>?start=<invite_code>`.

```json
{ "invite_code": "6a060e1bc41f" }
```

`invite_code` — `[A-Za-z0-9_-]`, 1–128 символов (сейчас коды — 12 hex-знаков,
`houses.invite_code`).

**Ответ 200:**

```json
{ "house": { "id": 1, "address": "…", "chat_link": "https://…", "emergency_phone": "+7 900 111-00-01",
             "has_gas": true, "uk_name": "ООО «УК Маяк»" }, "mismatch": false }
```

`house` — дом жителя **после** операции. `mismatch: true` — у жителя по данным УК
другой дом: вернулся он, а не дом из QR; в лог api пишется предупреждение.

**Ошибки:** `house_not_found` (404) — неизвестный код; `not_found` (404) — нет жителя.

#### `POST /residents/:id/house-by-address`

Дом по адресу, введённому жителем как есть.

```json
{ "address": "ул. Примерная, д. 3" }
```

`address` — 1–200 символов. Разбор — в api (`api/src/address.ts`): нижний
регистр, `ё`→`е`, без знаков препинания, типов улиц и «д./дом», город и хвост
«подъезд/кв.» отбрасываются; номер — последнее слово с цифрой, корпус и литера
приклеиваются («5 корп 2» → `5к2`). Сравнение — точное с `houses.street` /
`houses.number`, которые хранятся уже в таком виде.

**Ответ 200:** `{ "house": House }`.
**Ошибки:** `address_unrecognized` (400), `house_not_found` (404), `not_found` (404).

#### Объект `House`

| Поле | Тип | Может быть null | Смысл |
|---|---|---|---|
| `id` | number | нет | идентификатор дома |
| `address` | string | нет | человекочитаемый адрес — его показывает бот |
| `chat_link` | string | да | ссылка на чат дома; `null` — УК чат не завела |
| `emergency_phone` | string | да | телефон АДС дома для экстренных инструкций; `null` — бот называет 112 |
| `has_gas` | boolean | нет | `false` — в доме нет газа, бот не предлагает «Запах газа» |
| `uk_name` | string | да | название УК/ТСЖ дома — «оформлю срочную заявку в …» |

## Дома и жители — для УК

> ⚠️ **Внутренние, как и `/residents/*`:** снаружи всегда 404 (та же проверка
> заголовков прокси), через nginx не публикуются. Вызывает их команда УК на
> сервере — `docker compose exec api node dist/cli.js`, см. [`RUN.md`](RUN.md),
> «Дома и жители: команда УК». Входа для сотрудников УК пока нет, поэтому
> только изнутри сервера. Здесь телефон жителя в ответе **есть**: это рабочий
> список УК, а не ответ жителю.

Общее для тел запросов: лишние поля — `validation_error`; у необязательного поля
`null` — **стереть** значение, поле не передано — **не менять**.

### `GET /admin/houses`

Все дома. `?address=ул. Ленина, д. 5` — только дом с этим адресом (0 или 1 в
списке); адрес разбирается так же, как ввод жителя в боте.

**Ответ 200:** `{ "houses": AdminHouse[] }`. **Ошибки:** `address_unrecognized` (400).

### `POST /admin/houses`

```json
{ "address": "г. Тестоград, ул. Новая, д. 7 к 2", "chat_link": "https://max.ru/join/…" }
```

`address` — 1–200 символов, хранится как написан, а улица и номер для поиска
выделяются из него. `chat_link` — необязательный, `https://…`.
Код для QR (`invite_code`) генерирует БД.

**Ответ 201:** `{ "house": AdminHouse }`.
**Ошибки:** `address_unrecognized` (400); `conflict` (409) — дом с таким адресом
или такой же парой «улица + номер» уже есть.

### `PATCH /admin/houses/:id`

Тело — хотя бы одно из `address`, `chat_link` (`null` — убрать ссылку на чат).
**Ответ 200:** `{ "house": AdminHouse }`. **Ошибки:** `not_found`, `address_unrecognized`, `conflict`.

### Объект `AdminHouse`

| Поле | Тип | null | Смысл |
|---|---|---|---|
| `id` | number | нет | |
| `address` | string | нет | как написала УК |
| `street`, `number` | string | да | нормализованные — по ним житель находит дом вводом адреса |
| `chat_link` | string | да | ссылка на чат дома |
| `invite_code` | string | нет | код для QR `https://max.ru/<бот>?start=<код>` |
| `residents` | number | нет | жителей в доме, без архива |
| `created_at` | string | нет | ISO 8601 |

### `GET /admin/residents`

Фильтры: `house_id`, `phone` (`+7XXXXXXXXXX`), `include_archived=true` —
показать и архивных (по умолчанию их нет).
**Ответ 200:** `{ "residents": AdminResident[] }`.

### `POST /admin/residents`

```json
{ "phone": "+79990000000", "house_id": 4, "entrance": 2, "floor": 5,
  "apartment": "45А", "contract_number": "Д-123" }
```

| Поле | Обязательное | Ограничения |
|---|---|---|
| `phone` | да | `+7` и 10 цифр; уникален среди жителей **не в архиве** |
| `house_id` | нет | id дома |
| `entrance` | нет | целое 1–100 |
| `floor` | нет | целое −5…200 (0 и минус — цоколь, подвал) |
| `apartment` | нет | текст 1–16: «12», «12А», «12/1» |
| `contract_number` | нет | текст 1–64; справочное поле УК, у жителя не спрашивается, не уникален |

**Ответ 201:** `{ "resident": AdminResident }`.
**Ошибки:** `conflict` (409) — номер уже заведён; `invalid_reference` (400) — нет такого дома.

### `PATCH /admin/residents/:id`

Любые поля из `POST`, хотя бы одно. **Смена `phone` снимает привязку к MAX**
(`max_chat_id`, `max_user_id` → `null`): аккаунт подтверждал старый номер, с
новым житель войдёт в бота заново. Смена дома старые заявки не переносит —
у заявки своя копия дома.

**Ответ 200:** `{ "resident": AdminResident }`.
**Ошибки:** `not_found`; `resident_archived` (409) — житель в архиве;
`conflict`; `invalid_reference`.

### `POST /admin/residents/:id/archive`

Вместо удаления: житель не может войти (`link-by-phone` отвечает
`phone_not_registered`, `by-max-user` — `not_found`), привязка к MAX снимается,
заявки остаются. Номер можно завести заново — это будет новая запись.
Повторный вызов ничего не меняет. Возврата из архива нет — заводится заново.

**Ответ 200:** `{ "resident": AdminResident }`. **Ошибки:** `not_found`.

|---|---|---|---|
| `id` | number | нет | |
| `phone` | string | нет | `+7XXXXXXXXXX` |
| `house_id` | number | да | |
| `house_address` | string | да | адрес дома — чтобы не запрашивать отдельно |
| `entrance`, `floor` | number | да | подъезд, этаж |
| `apartment`, `contract_number` | string | да | квартира, номер договора |

## Мини-приложение — `/app/*` (публичные)

Единственные маршруты api наружу, кроме health: через nginx как
`https://<домен мини-аппа>/api/app/*`. Остальные маршруты по-прежнему
только изнутри сервера.

**Кто спрашивает** — по подписи, а не по запросу. Мини-апп кладёт
`WebApp.initData` в заголовок `X-Max-Init-Data`; api проверяет подпись токеном
бота (алгоритм — [`max-notes.md`](max-notes.md), «Проверка initData на
сервере»; код — `api/src/init-data.ts`), срок — сутки от `auth_date`. Из
подписанных данных берётся `user.id` — это аккаунт MAX, а житель — тот, к кому
аккаунт привязан входом в бота по контакту (`residents.max_user_id`). id жителя
с клиента не принимается: подать или увидеть чужую заявку нельзя.

| HTTP | `code` | Когда |
|---|---|---|
| 401 | `init_data_invalid` | заголовка нет, подпись не сошлась, данные старше суток |
| 403 | `not_linked` | подпись подлинная, но этот аккаунт MAX ещё не входил в бота |
| 503 | `miniapp_disabled` | у api не задан `MAX_BOT_TOKEN` — проверить подпись нечем |

### `POST /app/tickets/:id/cancel`

Отменить свою заявку — только «принятую» (`status: "new"`, решение 26.09.2026).
Заявка остаётся в БД со статусом `cancelled`. Житель уведомление о своей же
отмене не получает (api сразу отмечает его доставленным); отмену со стороны УК —
получает. **Ответ 200:** `{ "ticket": Ticket }`. **Ошибки:** `not_found` (404) —
чужая или нет такой; `not_cancellable` (409) — уже в работе или закрыта.

### `GET /app/me`

`{ "resident_id": 1, "house": House | null }` — дом с адресом, чатом, телефоном
АДС, газом и УК (объект `House`, как у бота).

### `GET /app/tickets`

`{ "tickets": Ticket[] }` — заявки жителя, новые сверху, активные и решённые,
не больше 50.

### `POST /app/tickets`

```json
{ "problem_type": "leak", "place": "in_apartment", "detail_code": "valve", "description": "течёт вентиль" }
```

Поля и маршрутизация — как у `POST /tickets` (общий код, `api/src/ticket-store.ts`),
но без `resident_id`: заявка создаётся от жителя из подписи. Коды — `^[a-z_]+$`.
**Ответ 201:** `{ "ticket": Ticket }`.

## Смена статуса и уведомления жителю

Петля «статус → уведомление»: УК/диспетчер меняет статус, бот сам пишет жителю.
Событие `status_changed` пишет **триггер БД** (миграция `0007`) — при смене через
api и при правке таблицы `tickets` напрямую (pgAdmin) одинаково.
Очередь — события заявки (`ticket_events`): смена статуса пишет
`status_changed`, доставка — `notified`. Все маршруты **внутренние** (снаружи 404).
Статус меняет только api, в MAX пишет только бот — токен бота в api не нужен.

### `GET /admin/tickets`

Заявки для УК/диспетчера, новые сверху, не больше 200. Фильтры: `house_id`,
`active=true` — только незакрытые. **Ответ 200:** `{ "tickets": AdminTicket[] }` —
поля заявки (как у `Ticket`) и `house_address`; телефона и данных MAX жителя нет.

### `POST /admin/tickets/:id/status`

```json
{ "status": "in_progress" }
```

`status` — `new` | `in_progress` | `resolved`. Статус и событие
`status_changed` (старый → новый) пишутся в одной транзакции.
**Ответ 200:** `{ "ticket": AdminTicket, "changed": true }`; `changed: false` —
статус уже был таким, событие не записано, уведомления не будет.
**Ошибки:** `not_found` (404), `validation_error` (400).

### `GET /notifications/pending`

Для бота: кому и о чём написать. `?limit=` 1–100, по умолчанию 20.

```json
{ "notifications": [ { "event_id": 7, "ticket_id": 1, "new_status": "in_progress",
  "problem_type": "heating", "responsible_name": "АО «Теплосеть»", "max_chat_id": 516093921 } ] }
```

- Берётся только **последняя** смена статуса каждой заявки: две смены подряд
  (в работе → решена) дают одно уведомление «решена», а не устаревшее «в работе».
- Недоставленное — если после события нет `notified`.
- Жители без привязки к MAX (не входили, в архиве) не попадают: писать некуда.

### `POST /notifications/:event_id/delivered`

Бот отправил уведомление — api пишет `notified`. Повторный вызов ничего не
дублирует. **Ответ 200:** `{ "ok": true }`. **Ошибки:** `not_found` (404) —
нет такого события смены статуса.

Бот вызывает его и когда написать жителю **нельзя** (MAX ответил 4xx, кроме
429, — например, бот заблокирован), иначе повторял бы попытку вечно; в логе бота —
предупреждение. Сеть, 5xx, 429 — уведомление остаётся в очереди.

## `POST /tickets`

Создаёт заявку от имени жителя. Вместе с заявкой в истории создаётся
событие `created` — в одной транзакции.

> ⚠️ **`/tickets` — внутренние маршруты**, как `/residents/*`: api верит
> переданному `resident_id`, поэтому снаружи всегда 404 (запросы с заголовками
> прокси отклоняются). Вызывает их бот. Мини-приложение получит свои маршруты
> с проверкой подписи `initData`.

**Тело запроса:**

```json
{ "resident_id": 1, "problem_type": "sparking", "place": null,
  "description": "искрит розетка на кухне" }
```

| Поле | Тип | Обязательное | Ограничения |
|---|---|---|---|
| `resident_id` | number | да | целое ≥ 1 |
| `problem_type` | string | да | 1–200 символов |
| `place` | string \| null | нет | 1–200 символов |
| `description` | string \| null | нет | 1–4000 символов — своими словами жителя |
| `detail_code` | string \| null | нет | `[a-z_]`, 1–64 — ответ на уточнение после типа (кнопка бота) |

**Ответ 201:**

```json
{
  "ticket": {
    "id": 1,
    "resident_id": 1,
    "house_id": null,
    "problem_type": "протечка трубы",
    "place": "подвал",
    "description": null,
    "status": "new",
    "assigned_organization_id": null,
    "deadline_at": null,
    "created_at": "2026-09-20T15:22:53.965Z",
    "updated_at": "2026-09-20T15:22:53.965Z"
  }
}
```

**Ошибки:** `validation_error` (400), `not_found` (404 — жителя с таким
`resident_id` нет или он в архиве), `bad_request` (400).

**Коды заявок** — по [`config/rules.yaml`](../config/rules.yaml) (Павел; бот переведён
на них 24.09.2026):

- обычная заявка: `problem_type` — тип (`type` в правилах): `leak`, `blockage`,
  `heating`, `electricity`, `elevator`, `common_area`, `structural`, `pests`,
  `other`; `place` — `in_apartment`, `entrance`, `whole_house`, `street`;
- аварийная заявка: `problem_type` — код опасности (`danger_types` в правилах):
  `gas_smell`, `exposed_wiring`, `flooding_threat`, `elevator_entrapment`;
  `place` — `null`. Приоритет «экстренная» = `problem_type` из этого списка,
  отдельного поля нет.

Место «двор» в `rules.yaml` местами называется `yard`; бот шлёт `street` — до
решения Павла. Из зоны собственника заявка приходит, только если житель нажал
«Всё равно передать в УК» — с тем же типом и местом.

**Маршрутизация при создании** (`api/src/routing.ts`, правила — `config/rules.yaml`).
Заявка сразу получает снимок результата: `rule_id`, `assigned_organization_id`,
`deadline_at`. Правка правил потом старые заявки не меняет.

- **Правило:** аварийная заявка (`problem_type` — id опасного правила) — это
  правило; иначе правила того же типа и места, где у правил с `detail` ответ
  жителя должен быть в списке, и правило с `detail` точнее общего.
  `detail_code: "owner_override"` («Всё равно передать в УК» из зоны
  собственника) → `other_unsure`. Ничего не подошло или тип «газ» в доме без
  газа → `other_unsure` (ручная классификация) и предупреждение в лог api —
  заявка не теряется.
- **Исполнитель** — по `responsible` правила: `management_company` — УК дома
  (`houses.organization_id`), `rso_*` — РСО дома по роли
  (`house_organizations`), `gas_emergency_service` и `owner` — `null`
  (городская служба 104 — не организация дома). Дом жителя неизвестен — `null`.
- **Срок** `deadline_at` = момент создания + `deadline_hours` правила; нет числа — `null`.
- `status` при создании всегда `"new"`.

`house_id` заявки копируется из жителя на момент создания. Если у жителя дом
не привязан — в заявке будет `null`.

## `POST /tickets/:id/cancel`

То же, что `/app/tickets/:id/cancel`, для бота: тело `{ "resident_id": 1 }`.
Внутренний.

## `GET /residents/:id/tickets`

Заявки жителя, новые сверху, не больше 50. `?active=true` — только незакрытые
(`new`, `in_progress`) — для «Мои заявки» в боте. Внутренний, как весь `/tickets`.

**Ответ 200:** `{ "tickets": Ticket[] }`.
**Ошибки:** `not_found` (404) — нет жителя или он в архиве; `validation_error` (400).

## `GET /tickets/:id`

Возвращает заявку по номеру — для «статус N» в боте. **Чья заявка, api не
проверяет:** бот сравнивает `resident_id` с жителем и на чужую отвечает так же,
как на несуществующую.

**Параметр пути:** `id` — целое число ≥ 1.

**Ответ 200:** тот же объект `{ "ticket": {...} }`, что у `POST /tickets`.

**Ошибки:** `not_found` (404), `validation_error` (400 — `id` не число).

## Объект `Ticket`

| Поле | Тип | Может быть null | Смысл |
|---|---|---|---|
| `id` | number | нет | номер заявки, его называют жителю |
| `resident_id` | number | нет | автор заявки |
| `house_id` | number | да | дом на момент создания |
| `problem_type` | string | нет | что случилось |
| `place` | string | да | где именно |
| `description` | string | да | своими словами жителя |
| `detail_code` | string | да | ответ на уточнение; `null` — уточнения не было |
| `rule_id` | string | да | правило `config/rules.yaml`, по которому направлена; `null` — заявка до маршрутизации |
| `responsible_name` | string | да | кто отвечает — для жителя: название организации дома или службы («аварийная газовая служба (104)»); `null` — назначить некого |
| `deadline_verified` | boolean | нет | срок правила сверен с первоисточником (`deadline_verified: true` в `rules.yaml`). `false` — `deadline_at` жителю **не показывать** |
| `status` | string | нет | `"new"` \| `"in_progress"` \| `"resolved"` |
| `assigned_organization_id` | number | да | исполнитель по правилу; `null` — городская служба, зона собственника или дом неизвестен |
| `deadline_at` | string | да | срок по нормативу, ISO 8601; `null` — в правиле нет числа |
| `created_at` | string | нет | ISO 8601 |
| `updated_at` | string | нет | ISO 8601, обновляется триггером БД |

## Чего ещё нет

Сознательно не реализовано на Д-9 — чтобы не фиксировать контракт раньше, чем
