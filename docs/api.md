# Контракт API

Сервис `api` диспетчера обращений. Документ описывает **реально работающие**
эндпоинты, а не план: всё перечисленное ниже проверено запросами.

Дата проверки: 21.09.2026 (Д-9, КТ-1).

> Контракт менять без предупреждения нельзя — на него завязан клиент.
> Если эндпоинт меняется, правится этот файл в том же коммите.

## Базовый адрес

| Окружение | Адрес |
|---|---|
| Локально (docker compose) | `http://localhost:3000` |
| Внутри сети compose | `http://api:3000` |

Порт задаётся переменной `API_PORT` (по умолчанию 3000).

## Общие правила

- Формат — JSON. Для запросов с телом обязателен заголовок
  `Content-Type: application/json`.
- Кодировка — UTF-8. Кириллица в полях поддерживается.
- **Идентификаторы — целые числа** (`number`), не строки. В БД это `BIGSERIAL`,
  драйвер приводит их к `number` (безопасно до 2^53).
- **Даты — строки ISO 8601 в UTC**, например `"2026-09-20T15:22:53.965Z"`.
- Поля в JSON — `snake_case`, как в БД.
- Лишние поля в теле запроса → ошибка `validation_error`, а не молчаливое
  игнорирование. Опечатка в имени поля обнаружится сразу.

### Формат ошибок

Любая ошибка возвращается в одинаковом виде:

```json
{
  "error": {
    "code": "not_found",
    "message": "Заявка 999 не найдена",
    "details": ["/problem_type must NOT have fewer than 1 characters"]
  }
}
```

- `code` — **часть контракта**, ветвиться в клиенте нужно по нему.
- `message` — текст для человека, формулировка может меняться.
- `details` — необязательное поле, присутствует только у `validation_error`.

### Коды ошибок

| HTTP | `code` | Когда |
|---|---|---|
| 400 | `validation_error` | тело не прошло проверку по схеме (тип, длина, лишнее поле) |
| 400 | `bad_request` | битый JSON, неверный `Content-Type`, несовпадение `Content-Length` |
| 400 | `invalid_reference` | ссылка на несуществующую запись (нарушение внешнего ключа) |
| 400 | `constraint_violation` | значение не прошло проверку на уровне БД |
| 404 | `not_found` | запрошенная сущность не найдена |
| 404 | `route_not_found` | такого маршрута не существует |
| 409 | `conflict` | запись с такими данными уже есть |
| 500 | `internal_error` | ошибка на стороне сервиса; подробности только в логах |
| 503 | — | только у `/health`, см. ниже |

## `GET /health`

Живость сервиса и соединения с БД. Используется healthcheck'ом docker-compose.

**Запрос:** без тела и параметров.

**Ответ 200** — всё работает:

```json
{
  "status": "ok",
  "service": "api",
  "db": "ok",
  "ts": "2026-09-20T15:22:40.692Z"
}
```

**Ответ 503** — сервис жив, но БД недоступна:

```json
{
  "status": "degraded",
  "service": "api",
  "db": "down",
  "ts": "2026-09-20T15:22:40.692Z"
}
```

Формат ответа одинаковый у 200 и 503 — ошибочного конверта здесь нет.

| Поле | Тип | Значения |
|---|---|---|
| `status` | string | `"ok"` \| `"degraded"` |
| `service` | string | всегда `"api"` |
| `db` | string | `"ok"` \| `"down"` |
| `ts` | string | ISO 8601 |

## `POST /residents/find-or-create`

Находит жителя по `max_chat_id` или создаёт нового. **Идемпотентен**: повторный
вызов с тем же `max_chat_id` вернёт того же жителя, не создавая дубля.

**Тело запроса:**

```json
{ "max_chat_id": 516093921, "house_id": 2 }
```

| Поле | Тип | Обязательное | Ограничения |
|---|---|---|---|
| `max_chat_id` | number | да | целое ≥ 1, `chat_id` диалога в MAX |
| `house_id` | number \| null | нет | целое ≥ 1, дом жителя, если известен |

Если житель уже есть, а `house_id` передан — он будет записан. Если передан
`null` или не передан вовсе, уже сохранённый `house_id` **не затирается**.

**Ответ 200:**

```json
{
  "resident": {
    "id": 1,
    "max_chat_id": 516093921,
    "house_id": null,
    "created_at": "2026-09-20T15:21:32.256Z"
  },
  "created": true
}
```

| Поле | Тип | Смысл |
|---|---|---|
| `resident.id` | number | идентификатор жителя |
| `resident.max_chat_id` | number | `chat_id` диалога в MAX |
| `resident.house_id` | number \| null | дом, если привязан |
| `resident.created_at` | string | ISO 8601 |
| `created` | boolean | `true` — создан этим запросом, `false` — уже существовал |

**Ошибки:** `validation_error` (400), `invalid_reference` (400 — `house_id`
указывает на несуществующий дом).

Обрати внимание: создание отвечает **200**, а не 201 — эндпоинт не гарантирует
создание, поэтому различать надо по полю `created`.

## `POST /tickets`

Создаёт заявку от имени жителя. Вместе с заявкой в истории создаётся
событие `created` — в одной транзакции.

**Тело запроса:**

```json
{ "resident_id": 1, "problem_type": "протечка трубы", "place": "подвал" }
```

| Поле | Тип | Обязательное | Ограничения |
|---|---|---|---|
| `resident_id` | number | да | целое ≥ 1 |
| `problem_type` | string | да | 1–200 символов |
| `place` | string \| null | нет | 1–200 символов |

**Ответ 201:**

```json
{
  "ticket": {
    "id": 1,
    "resident_id": 1,
    "house_id": null,
    "problem_type": "протечка трубы",
    "place": "подвал",
    "status": "new",
    "assigned_organization_id": null,
    "deadline_at": null,
    "created_at": "2026-09-20T15:22:53.965Z",
    "updated_at": "2026-09-20T15:22:53.965Z"
  }
}
```

**Ошибки:** `validation_error` (400), `not_found` (404 — жителя с таким
`resident_id` нет), `bad_request` (400).

> ⚠️ **Пока всегда `status: "new"`, `assigned_organization_id: null`,
> `deadline_at: null`.** Это не ошибка: маршрутизация по `config/rules.yaml`
> появится на Д-8, до этого заявке некому назначать исполнителя и неоткуда
> брать срок. Клиенту стоит уже сейчас рассчитывать на то, что эти поля
> заполнятся, но быть готовым к `null`.

`house_id` заявки копируется из жителя на момент создания. Если у жителя дом
не привязан — в заявке будет `null`.

## `GET /tickets/:id`

Возвращает заявку по номеру. Понадобится для команды «Статус».

**Параметр пути:** `id` — целое число ≥ 1.

**Ответ 200:** тот же объект `{ "ticket": {...} }`, что у `POST /tickets`.

**Ошибки:** `not_found` (404), `validation_error` (400 — `id` не число).

---

## Объект `Ticket`

| Поле | Тип | Может быть null | Смысл |
|---|---|---|---|
| `id` | number | нет | номер заявки, его называют жителю |
| `resident_id` | number | нет | автор заявки |
| `house_id` | number | да | дом на момент создания |
| `problem_type` | string | нет | что случилось |
| `place` | string | да | где именно |
| `status` | string | нет | `"new"` \| `"in_progress"` \| `"resolved"` |
| `assigned_organization_id` | number | да | исполнитель (Д-8) |
| `deadline_at` | string | да | срок по нормативу, ISO 8601 (Д-8) |
| `created_at` | string | нет | ISO 8601 |
| `updated_at` | string | нет | ISO 8601, обновляется триггером БД |

## Чего ещё нет

Сознательно не реализовано на Д-9 — чтобы не фиксировать контракт раньше, чем
сложится логика:

- обновление статуса заявки (`PATCH /tickets/:id`);
- список заявок жителя и список для диспетчера;
- маршрутизация: заполнение `assigned_organization_id` и `deadline_at`;
- эндпоинты справочников (`organizations`, `houses`, `routing_rules`).

Если что-то из этого нужно раньше срока — скажи, добавим и опишем здесь.
